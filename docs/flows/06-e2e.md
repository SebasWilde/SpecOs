# Flow: /specos-e2e

> **When to run:** QA (human or agent), after the test cases are expanded and the spec is approved.
> **What it does:** Automates the expanded test cases in the e2e repo, one test per case, the way that repo already writes tests, and closes with a block for its PR.

## Notes

- The unit is the test case, not the task: the skill reads no `tasks.md` and needs no ticket key.
- It refuses a spec with `status: draft` and any case that covers a `[pending]` AC. Sketches (no `steps:`) are listed and skipped.
- If `testcases.md` was reviewed against an older spec version than the current one, it warns once and continues.
- The spec decides *what* is tested; the e2e repo decides *how* (tool, selectors, page objects, fixtures, reporting, layout). The skill names no tool.
- Every test carries the case id **and** the feature name. The exact form of the label comes from the e2e repo or a `rules` entry for role `e2e`; with neither, the agent proposes `<feature>/TC-XX` and asks.
- A test that fails because the app does not meet the spec stays red and is reported — a code defect becomes a short bug text, a gap in the spec follows the change request protocol. Tests are never bent to pass.
- The closing block is printed, not written to a file. The agent never commits on its own.
- When `implementation_repos.e2e` is `null` (and some other repo has a path), the agent asks once: "Is there an e2e repo for this project? Give me its path from this folder, or say there is none." QA gives the path (for example `../repo-e2e`), the agent checks it is reachable, writes it to `implementation_repos.e2e` in `local-workspace.yml` (local, never committed) and continues. If there is none, it says there is nowhere to automate, stops, leaves the key as `null` and does not ask again in that session. With every path `null` the project is a monorepo: no question, it works in the current directory.
- `e2e_modes` in `local-workspace.yml` lists how QA runs the tests (`native`, `docker` or both). If it is missing the agent asks once and saves it; with one mode it runs in it, with two it asks which one for that run. In `docker` mode the stack must be up from the repo's docker checkout.
- If the existing tests write the feature name differently from the spec folder (`1-checkout` and `01-checkout`), the agent warns once and asks which form to use for the new tests: the folder name or the form the repo already uses. It never chooses on its own and never renames existing tests; the QA decides whether to align them.
- A `testcases.md` with no `spec:` stamp, or a case with no `covers:`, predates the current format: the agent says so once and continues, marking the ACs it shows for that case as inferred.
- When a case needs a test id or a way to prepare data the e2e repo does not have, the agent asks the Lead before reading the frontend or backend, only for what is missing.
- Before closing it runs the e2e repo's own review (or a short list) on the files it touched and copies the repo's own command to watch the run and open the report. The closing block gains `Files changed:`, `Review:` and `Evidence:`.
- Like `/specos-dev`, it resolves the e2e repo's memory before reading it (see the memory links note in flow 03) and writes what stays true back to that repo's memory.
